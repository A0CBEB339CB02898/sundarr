# 资源搜索

本文档统一定义 SOURCE 插件、搜索处理管线和按需详情协议。`SOURCE` 只搜索具体资源及链接候选，不承担媒体目录、想看同步或文件搬运。

状态：Core 搜索、两阶段详情、收藏标记和 Web Console 已实现；真实 SeedHub 插件位于 `sundarr-sources`，仍需 Manifest v2 与 Core 端到端验收。

## 1. 数据流

```text
SearchQuery
  -> 并发 SOURCE Adapter
  -> RawSearchItem
  -> 文本解析与链接提取
  -> 字段标准化
  -> 跨源去重与排序
  -> 收藏状态标记
  -> ResourceCandidate
```

搜索始终实时调用已启用 SOURCE。收藏库只附加 `is_favorited`，不能替代搜索源，也不能让搜索结果自动入库。

## 2. SOURCE 运行合同

### 2.1 SearchQuery

- `keyword` 必填。
- `result_type` 可取 `all`、`magnet`、`quark`、`aliyun`、`baidu`、`xunlei` 或 `unknown`。
- `limit` 由 Core 限制上限。
- Adapter 不得修改输入对象。

### 2.2 RawSearchItem

必需字段：

```text
source_id
source_type
raw_title
raw_content
fetched_at
```

可选字段包括 `raw_url`、`published_at` 和 `metadata`。`metadata` 可提供 `year`、`quality`、`link_name` 等源站可稳定解析的信息；Core 对缺失字段执行保守兜底，不得编造年份、类型、季集或质量。

Adapter 只负责访问目标站点并转换原始结果，不负责：

- ORM 持久化、收藏状态或任务创建；
- 跨源去重、最终排序和链接有效性策略；
- 下载、转存或 SMB 访问。

### 2.3 SourceModel

最小运行时字段：

```text
id
name
description
homepage_url
search_function
test_function（可选）
fetch_detail_function（可选）
```

`SourceModel.id`、Manifest `plugin_id` 和 `RawSearchItem.source_id` 必须一致。v2 插件入口通过 `PluginContext` 返回符合合同的实例；flat v1 只保留历史 SOURCE 兼容。

## 3. 两阶段详情

有详情页的站点应避免搜索时抓取每个结果的完整链接：

1. 第一阶段只请求列表页并返回标题、年份、来源页和 `has_more_links=true`。
2. 用户显式点击“加载链接”后，Core 按 `source_id + detail_url` 调用 `fetch_detail_function`。
3. 一步源可在第一阶段直接返回链接，`fetch_detail_function` 为空。

核心接口：

```text
GET  /search
POST /search/detail
```

`detail_url` 必须来自该 Source 的搜索结果；Adapter 应限制允许访问的主机和路径，不能把它变成通用 SSRF 入口。

SeedHub 的预期行为是列表页一次轻量搜索，详情和跳转链接仅在用户请求对应候选时解析。

## 4. 处理管线

### 4.1 解析与链接提取

Core 从 HTML、纯文本或 Markdown 中提取可识别链接，并处理链接与提取码不在同一行、同一文本多链接和广告混杂等情况。链接提取器和验证器是 Core 或 SOURCE 内部能力，不是顶层插件类型。

### 4.2 标准化

资源级候选保留：

```text
title
normalized_title
original_title
year
links
is_favorited
```

链接级结果保留：

```text
provider
name
url
code
quality
valid / validation_status / validation_message / checked_at
source_id / source_url
is_favorited
```

`quality` 和具体链接展示名属于 `ResourceLink`，不属于 `Resource`。无法识别字段使用 `null` 或 `unknown`。

### 4.3 去重

- 资源优先按规范标题与年份归组；置信度不足时保留为独立候选。
- 同一规范 URL 只保留一次。
- 同一资源可以保留不同 Provider 或不同质量的多个链接。
- 来源字段必须保留，不能在合并时丢失可追踪性。

### 4.4 有效性检测

- 磁力、thunder、ed2k 等协议只做格式判断，不承诺资源活性。
- 404/410 可判定为 `invalid`。
- 401/403/405/429 应判定为 `unknown`，避免把权限或限流误判为失效。
- 未知 Provider 使用轻量 HEAD/GET 兜底，并受超时与请求安全限制。

### 4.5 排序与缓存

排序可以组合标题匹配、来源权重、新鲜度、链接状态和质量，但评分只属于搜索过程，不作为持久业务事实。普通关键词缓存建议 10 分钟，热门关键词 1 小时，失败 Source 可短期熔断 5 分钟。

## 5. 错误隔离

默认限制：单 Source 10 秒、全局搜索 15 秒、最多 5 个 Source 并发。Adapter 不得无限重试或超过 Core 全局截止时间。

标准错误：

```text
SEARCH_SOURCE_TIMEOUT
SEARCH_SOURCE_FAILED
SOURCE_CONFIG_INVALID
SOURCE_PARSE_FAILED
```

单个 Source 超时或异常不得使整体搜索失败；响应和诊断必须标明失败来源。

## 6. 收藏边界

- 收藏资源：写入或更新 `Resource.favorited_at`。
- 收藏链接：写入最小父 `Resource` 和对应 `ResourceLink`；父资源本身不一定收藏。
- 取消收藏不影响实时搜索源。
- 刷新资源由用户显式重新搜索；刷新链接只重新验证该链接。
- 当前任务事实仍来自远程媒体库扫描，收藏不自动创建 `TransferTask`。

## 7. Web Console

`/app/search` 专门承载具体资源搜索，与 `/app/discover` 媒体目录发现分离。搜索和收藏页面支持网格/列表展示、按需加载链接、失败重试和收藏状态。

Sources 页面只展示已安装搜索源、测试入口和诊断，不在线创建、编辑或保存 Python Adapter。

## 8. 验收标准

- 多 Source 可并发调用，单源失败不影响整体结果。
- 一步源和两步源均符合合同。
- 轻量搜索不会为每条 SeedHub 结果预抓详情。
- 标准化、链接提取、去重、排序和收藏标记有离线测试。
- `detail_url` 访问边界和日志脱敏有测试。
- 真实 SeedHub 搜索与详情通过显式集成测试，并回归 Core API 和页面。
